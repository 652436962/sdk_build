# T527（飞凌 OKT527-C）温度误关机分析报告

| 项目 | 内容 |
|---|---|
| 平台 | 全志 T527（sun55iw3p1），飞凌 OKT527-C 核心板 |
| 系统 | OKT527-linux-sdk（Linux 5.15.147 #41，镜像构建 2026-09-16 15:14，pack 15:16） |
| 板卡标识 | `OK527`，SoC 串口 `root@OK527`，网络 `192.168.1.232` |
| 现象 | 烧录镜像后启动约 **8.6 s** 出现 `reboot: Power down`，板子断电 |
| 报告日期 | 2026-09-16 |
| 结论 | **不是真实过热、不是芯片/板卡损坏，而是 THS 温度读数在"负载/电源域动作"瞬间被毫秒级扰动，叠加驱动缺少异常值剔除（去毛刺），导致 `critical` 误触发 → 热保护主动关机** |

---

## 1. 现象与关机链路

串口日志（`session-_dev_ttyACM0-2026-09-16T08-32-52.log` 第 2382~2463 行、3503~3580 行）：

```
[    8.627439] thermal thermal_zone0: cpul_thermal_zone: critical temperature reached, shutting down
[    8.637435] reboot: HARDWARE PROTECTION shutdown (Temperature too high)
[    8.751481] reboot: Hardware protection timed-out. Trying forced poweroff
[    9.630244] reboot: Power down
```

链路（源码位置均已核对）：

```
温区采样值 >= critical trip（cpul_thermal_zone，当前 DTB 为 130000）
  └─ drivers/thermal/thermal_core.c:327  thermal_zone_device_critical()
       └─ hw_protection_shutdown("Temperature too high", CONFIG_THERMAL_EMERGENCY_POWEROFF_DELAY_MS=100)
            └─ kernel/reboot.c:530  hw_failure_emergency_poweroff_func()  → 超时后 kernel_power_off()
                 └─ printk "reboot: Power down" → machine_power_off()
```

**关键认识：`Power down` 是内核按热保护流程主动关机。**它既不是掉电、欠压、看门狗，也不是烧录失败或文件系统损坏（每次都能正常引导到 `/init`，rootfs 正常挂载）。

涉及的温区与传感器：

| 温区 | 类型名 | 传感器 | 说明 |
|---|---|---|---|
| thermal_zone0 | `cpul_thermal_zone` | `<&ths1 1>`（ch1, `0x020094C4`） | 出问题的温区 |
| thermal_zone1 | `cpub_thermal_zone` | `<&ths1 0>`（ch0, `0x020094C0`） | 同步被扰动 |
| thermal_zone2 | `gpu_thermal_zone` | `<&ths1 2>`，驱动内部改用 ch3 数据 | |
| thermal_zone3 | `npu_thermal_zone` | `<&ths1 3>`（ch3, `0x020094CC`） | |
| thermal_zone4 | `ddr_thermal_zone` | `<&ths0 0>`（`0x0200A0C0`） | 本板该通道恒为错误值（另议） |
| thermal_zone5 | `axp2202-usb` | AXP2202 PMU 内部温度 | 作为"板级温度"旁证 |

驱动实现：`bsp/drivers/thermal/sunxi_thermal.c`（`sun55iw3_ths1_get_temp()`、`sun55iw3_ths1_calibrate()`）。

## 2. 证据链

### 2.1 镜像阈值已被临时抬高到 130 ℃，仍然关机

`OKT527-C-Common.dtsi` 末尾（2026-09-16 15:14 写入）有一段临时诊断代码，把 `cpul/cpub/gpu` 的 `cpu_crit` 从
110 ℃（`bsp/configs/linux-5.15/sun55iw3p1.dtsi` 基础值）/115 ℃（`FET527.dtsi:912` 板级值）抬到 **130 ℃**。

从打包产物 `out/t527/okt527/buildroot/boot.img` 中抠出 fdt 反编译确认（`0x1FBD0 = 130000`）：

```
cpul_thermal_zone: cpu_crit@0 { temperature = <0x1fbd0>; type = "critical"; }
cpub_thermal_zone: cpu_crit@0 { temperature = <0x1fbd0>; type = "critical"; }
gpu_thermal_zone:  gpu_crit@0 { temperature = <0x1fbd0>; type = "critical"; }
```

**→ 阈值已是 130 ℃ 仍触发，说明当时内核读到的 cpul 值 ≥130 ℃。**

### 2.2 触发是"概率性 + 固定时刻"，不符合真实热过程

| 日志 | 启动次数 | 热关机次数 | 触发时刻 |
|---|---|---|---|
| `session-...06-54-50.log` | 4 | 1 | 8.624 s |
| `session-...08-32-52.log` | 3 | 2 | 8.627 s / 8.629 s |
| 2026-09-16 17:5x（SSH 手工读数那次） | 1 | 0 | — |
| 2026-09-16 17:49（抓取的那次） | 1 | 1 | ~8.6 s 后断电（抓到现场，见 2.5） |
| 2026-09-16 18:02（8 核满载复现） | — | 1 | 满载测试中被关机（见 2.6） |

同一份固件（DTS/DTB/镜像自 15:14/15:16 起未改动）有时关机、有时不关机，且触发都落在 **8.62~8.63 s**
（温区在内核约 0.4 s 注册、轮询周期 1 s，故这是第 8~9 次轮询，正好压在 `mali_kbase` / `npu vipcore` /
`camera is on, close dfs` / udev 那一串事件上）→ **不符合真实热过程的特征**。

### 2.3 上板寄存器实读：校准数据存在且已写入（排除"校准缺失"）

|---|---|---|
| `0x02009400` CTRL0 | `0x01DF002F` | T_ACQ=47、FS_DIV=479 |

| `0x02009408` PC | `0x0001C000` | TEMP_PERIOD=28 |

### 2.5 现场抓取：决定性的 3 行（被关机那一次启动）

抓取文件：`captures/ths-boot-20260916-175557.log` 前 3 行（热保护断电前最后一刻，写回恰好落盘）：

```
[THS] up=8.53 z0=51282 z1=51800 z2=51356 z3=51356 z4=-31154 z5=43900 raw_c0=2043 raw_c1=1988
[THS] up=8.67 z0=52836 z1=52318 z2=64805 z3=64805 z4=-2072  z5=44500 raw_c0=998  raw_c1=2022
[THS] up=8.75 z0=101465 z1=118755 z2=108550 z3=108550 z4=67730 z5=44500 raw_c0=654 raw_c1=739
```

解读：

* **8.53 s**：z0=51.3 ℃ / z1=51.8 ℃，全通道正常（原始码 2043 / 1988）；
* **8.67 s**：cpub（ch0）原始码骤降到 **998**（换算 ≈118.8 ℃），而 cpul（ch1）仍正常（码 2022）；
* **8.75 s**：**所有 ths 通道同时**跳到 101~119 ℃，码降到 654 / 739（换算 ≈136~141 ℃）→ 随即断电；
* 从 51.8 ℃ 到 >130 ℃ **只间隔 ≤0.14 s**（相邻两个样本间隔 140 ms）。

### 2.6 8 核满载复现（可重复触发）

```
t=113.39  z0=73905(73.9C) z1=72020(72.0C) z5=42100
          c0=0x2D2(722 → 136.7C)  c1=0x2CD(717 → 137.2C)
```

* 同一时刻：sysfs 温区报 73.9 / 72.0 ℃，而 devmem 直读原始码算出 **136~137 ℃** —— **两条读取路径在同一秒内自相矛盾**，
  说明原始码本身在毫秒级被扰动；
* 约 1 s 后内核 1 Hz 轮询读到 >130 ℃ → 再次热保护关机（板子掉线，需重新上电）。

### 2.8 数据手册/用户手册中影响 THS 读数的因素（逐条对照本 SDK）

来源：`datasheet/t527/T527_User_Manual_V0.90.pdf` 第 2.16 章（THS）、第 2.16.3~2.16.6 节（时序、公式、寄存器）、
`T527_Datasheet_V0.90.pdf` 第 3.9.8 节（特性）、第 6.6 节（GPADC 电气特性）、第 7.1/7.2 节（温度与封装热特性）。

**（1）结构与规格（UM 2.16.1）**

* 5 个片上传感器：**THS1_0=大核、THS1_1=小核、THS1_2=GPU、THS1_3=NPU、THS0_0=DDR**（与本板 DTS 的
  `cpub→<&ths1 0>`、`cpul→<&ths1 1>` 一致）；
* 精度规格：**±5 ℃（-40~+60 ℃）、±3 ℃（+60~+125 ℃）**；带平均滤波；支持过温保护中断与告警中断。

**（2）转换公式（UM 2.16.3.4）与驱动实现一致**

```
-40 ℃ ~ +55 ℃ : T = (sensor_data - 2736) / (-13.54)
+55 ℃ ~ +125 ℃: T = (sensor_data - 2825) / (-15.33)
```

驱动的 `sun55iw3_calc_temp()` 用 `(2736-code)*0.074` / `(2825-code)*0.065`（即 1/13.54 与 1/15.33 的近似），
分界 1991 对应手册的 55 ℃（按手册算为 1982）→ **公式与实现一致，本报告附录 B 的码值-温度表与手册吻合**。

**（3）时序约束（UM 2.16.3.2，CLK_IN=24 MHz）**

```
CONV_TIME = 1/24MHz × 14 = 0.583 us
TACQ      > 1/24MHz × 24 ≈ 1 us
THERMAL_PER > ADC_Sample_Frequency(周期) > TACQ + CONV_TIME
测温周期 THERMAL_PER = 4096 × (n + 1) / CLK_IN     ← UM 2.16.6.3（THS_PER[31:12]）
```

**（4）影响读数的因素对照表**

| # | 因素（手册依据） | 手册要求 / 默认值 | 本 SDK 驱动现状 | 能否解释本次现象 |
|---|---|---|---|---|
| 1 | 校准数据 `THSn_CDATA`（UM 2.16.6.18/19、SID Table 2-21：T-sensor Calibration 0x3B-0x3F 与 0x44-0x48，含 ROOM 与各传感器校准码） | 使能前从 SID 读出并写入 CDATA | ✅ 已读已写（实测 `0x020094A0=0x083C0841`、`A4=0x0845083C`） | ❌ 不是原因 |
| 2 | 传感器精度（UM 2.16.1） | ±5 ℃ / ±3 ℃ | 实测跳变 **60~80 ℃** | ❌ 远超精度规格 → 属功能性扰动，非精度/校准问题 |
| 3 | 采样时钟 CLK_IN（UM 2.16.3.1：DCXO24M + PCLK） | 24 MHz | CCU 中 `gpadc0/1_24m` 的父时钟**只有 `dcxo24M`**（无 PLL 选项），来源稳定 | ⚠️ 时钟源本身稳定；但 bus 时钟 `CLK_THS`（PCLK）随系统变化 |
| 4 | 采集时间 `TACQ`（THS_CTRL[15:0]） | 手册示例 `0x2F`（47 ≈ 1.96 µs > 1 µs） | 驱动写 `T_ACQ(47)` ✅ | ❌ 合规 |
| 5 | 采样分频 `FS_DIV`（THS_CTRL[31:16]） | 手册示例 `0x1DF`（479 → 采样周期 ≈20 µs > TACQ+CONV 2.54 µs） | 驱动写 `FS_DIV(479)` ✅ | ❌ 合规 |
| 6 | 测温周期 `THERMAL_PER`（THS_PER[31:12]） | 芯片复位值/手册示例 **`0x3A`(58) = 10 ms** | 驱动改成 **`28` = 4.95 ms**（实测 `THS_PER=0x0001C000`） | ⚠️ **唯一与手册/默认不一致的配置**，不违反时序约束，建议做 A/B 实验 |
| 7 | 平均滤波（`THS_FILTER` 0x30：EN + Average Filter Type 00→2、01→4、10→8、11→16 点） | 可配 2/4/8/16 点平均 | 驱动 `EN=1, TYPE=1` → **4 点平均**，窗口 ≈4×4.95 ms ≈ **20 ms** | ⚠️ **窗口 ≤79 ms（即便选最大 16 点）< 扰动时长 ~140 ms → 硬件滤波挡不住** |
| 8 | 数据有效位 `THS_DATA_INTS`（0x20，每传感器 1 bit，R/W1C） | 读 1 = 转换完成 | 驱动检查 `BIT(id)`（实测 `0x0F`） | ⚠️ 只能说明"转换完成"，不能保证数据未被扰动 |
| 9 | 硬件过温保护/告警阈值（`0x40~0x4C` 告警默认约 90 ℃、`0x80/0x84` 关机默认约 102 ℃）及其中断 | 可配置并开中断 | **驱动完全未配置、未启用** | ⚠️ ①没有硬件兜底；②这些比较器也是**现成的扰动量测手段**（用告警中断计数即可量化扰动） |
| 10 | 结温上限（Datasheet Table 7-2） | **正常工作 Tj ≤ 115 ℃；破坏性 125 ℃（任何情况不得超）** | 临时 DTS 把 critical 抬到 **130 ℃（> 破坏性温度）** | ❌ 该临时值必须回退；同时"读出 130 ℃ 的芯片还活着"本身就是矛盾 |

**（5）从手册角度看本次现象的定位**

* 校准、时序（TACQ / FS_DIV）、时钟源三项都**合规**，排除；
* 手册给的精度是 ±3~5 ℃，而我们观测到的是**毫秒级 60~80 ℃ 的跳变**，属于功能性扰动（模拟前级/采样被扰动），
  不是精度或校准问题；
* 硬件**平均滤波窗口太短**（驱动 4 点 ≈20 ms；手册最大 16 点也仅 ≈79 ms），挡不住 ~140 ms 的扰动 —— 这是
  "异常值直接进入 critical 判定"的硬件侧原因；软件侧则是驱动**没有任何合理性校验（去毛刺）**；
* GPADC 的参考是 **VCC-ADC（0~1.8 V 满量程，UM 3.12.5 / Datasheet Table 6-6）**，即该模拟簇的读数与模拟参考/供电
  强相关：参考或采样建立被负载瞬态扰动时，码值会整体偏移（**码变小 → 温度读数偏高**），这与我们观测到的
  "码从 ~2050 掉到 ~650~750 再恢复"方向一致（注：纯参考跌 3 倍不现实，更可能是采样建立不足/参考噪声/地弹
  共同作用；THS 手册未给出自身参考源，此项为推断）；
* 硬件告警/关机比较器驱动都没启用，所以唯一在起作用的是"模拟值 + 4 点平均 + 软件 critical 判定"，
  一次扰动即可触发不可逆关机。

**（6）基于手册的后续实验建议（成本低、可量化）**

1. **A/B 实验**：把 `PC_TEMP_PERIOD(28)` 改回手册默认 `58`（10 ms），比较扰动出现率是否变化；
2. **加长滤波**：`FILTER_TYPE` 由 1（4 点）改 3（16 点），观察扰动幅度/宽度变化（用于确认是否需要软件去毛刺）；
3. **用硬件告警做探测器**：把 `0x40~0x4C` 告警阈值（默认约 90 ℃）按需下压到 ~75 ℃ 并打开告警中断，
   统计满载/启动各阶段的中断次数 —— 可量化"扰动有多频繁"；
4. **根治仍靠软件去毛刺**（报告 5.1）：硬件滤波窗口最多 79 ms，覆盖不了 140 ms 级扰动。

### 2.9 哪些 IO/引脚会影响 THS 读数（手册引脚级证据）

**（1）THS 本身没有任何对外引脚**

`T527_Datasheet_V0.90.pdf` 的引脚表里搜不到 THS 相关引脚；5 个传感器都是**片上**的
（THS1_0 大核 / THS1_1 小核 / THS1_2 GPU / THS1_3 NPU / THS0_0 DDR）。
→ 不存在"某根 IO 直接接到温度传感器"这种通路，只能是**共用模拟资源 / 电源地 / 时钟**三条间接耦合。

**（2）唯一的模拟域引脚（与 GPADC/LRADC 共用参考与前级）**

| 引脚 | 球号 | 类型 | 供电域 | 手册描述 |
|---|---|---|---|---|
| VCC-ADC | W7 | P | — | **Power Supply for GPADC and LRADC**（即该模拟簇的参考/供电） |
| VREFN-ADC | Y10 | P | — | **GPADC Reference Voltage (Negative)**（参考负端/模拟地） |
| VCM-ADC | Y9 | A I/O | VCC-ADC | **External Capacitor Connection**（共模脚，外接电容） |
| GPADC0~23 | W1, W2, W3, W4, W5, W6, Y2, Y3, AA1, AA2, AA3, AA4 … AE6 | AI | VCC-ADC | 模拟输入，0~1.8 V 满量程 |
| LRADC0/1 | V3 / V2 | AI | VCC-ADC | 低精度 ADC 输入 |

手册 3.12.5 / Table 6-6：GPADC **Power reference voltage = VCC-ADC**，输入 0~1.8 V，12 bit（有效 10 bit），
最大 1 MS/s，转换 13 个 ADC 时钟。
→ 该簇的读数是**相对 VCC-ADC 的比例量**：VCC-ADC / VREFN-ADC / VCM-ADC 网络上的纹波、跌落、地弹会同时改变
采样码值；**码变小 = 温度偏高**，与我们实测方向一致（~2050 → ~650~750）。

**（3）本板这些模拟脚的实际用法（`OKT527-C-Common.dtsi`）**

| 用途 | 通道 | 对应球号 |
|---|---|---|
| NTC 温度采集 | GPADC0 CH3 | W4 |
| 分压电压采集 | GPADC0 CH4 | W5 |
| 电流采集 | GPADC0 CH6 | Y2 |
| GPADC1 | `channel_select = <0x1ff>`（CH0~CH8 全开） | 对应 Y3/AA1… |
| 6 键键盘 | LRADC0/1，`&lradc status = "okay"`，`key_cnt = <6>` | V2 / V3 |

即：本板上 VCC-ADC 域共有 **GPADC0 的 5 个通道 + GPADC1 的 9 个通道 + LRADC 键盘** 在活动
（LRADC 键盘驱动 1.05 s 就注册了 input 设备，属周期性扫描）。

**（4）时钟/数字侧（不产生模拟偏差，但能破坏转换）**

* `CLK_GPADC1_24M` → THS1 的采样时钟（DTS `clock-names = "sclk"`）；`CLK_GPADC0_24M` → THS0 的；
  两者在 CCU 中的父时钟**只有 `dcxo24M`**（`ccu-sun55iw3.c`：`gpadc0_24m_parents[] = { "dcxo24M" }`）；
* 全 SDK 中取用这两路 24M 时钟的**只有 ths 驱动**（GPADC 驱动只取 `bus` 时钟）→ 目前没有别的驱动会改它；
* `CLK_THS` + `RST_BUS_TH`：THS 寄存器接口时钟/复位（纯数字域）。

**（5）板级大电流 IO（间接，但实测最重要）**

WiFi/BT 电源使能 PK6（本 DTS 用 gpio-leds 默认常开）、4G 模组、USB Hub、摄像头（PE13/PE14 + MIPI）、
LCD 背光 PWM、用户 LED PJ24、PG0(LEDC)、PG10~PG14(I2S1) 等，**都不与 THS 直连**，但会改变整板电流
→ 电源/地平面噪声 → 模拟参考。
**关键实测：纯 8 核 CPU 满载即可复现码值崩塌（没有任何 IO 动作参与）**，说明主因是 **SoC 自身电流/电源域瞬态**，
而不是某根引脚；IO 只能通过上面这些间接途径**加剧或触发**。

**（6）需要核对的 IO 配置隐患**

启动日志（每次都有）：

```
sunxi:pinctrl_sunxi:[WARN]: bank[G] power mode not correct, power_val=1800000, power_sel=3300000
sunxi:pinctrl_sunxi:[WARN]: bank[M] power mode not correct, power_val=1800000, power_sel=3300000
```

（`bsp/drivers/pinctrl/pinctrl-sunxi.c:785`：实际供电 1.8 V < DTS 声明 3.3 V）。这类**耐压/电平配置不一致**
会导致输入级漏电，理论上可向 die 注入电流、扰动模拟域。本板上 PG 用于 PG0(LEDC)、PG10~PG14(I2S1)，
PM 用于 PM0/PM1，建议核对这些脚上是否真有 3.3 V 器件、以及 bank 供电与 DTS 声明是否应改为 1.8 V。

**（7）据此可做的定位实验（按性价比排序）**

1. **逐个关外设 + 8 核满载对照**：PK6(WiFi/BT 电源)、摄像头、4G、LCD 背光、LED、I2S1 → 看码值是否还跳；
2. **把 GPADC/LRADC 当扰动探测器**：
   ① 先**停掉你自己的 CH3 采样脚本**再满载（排除"我们的采样本身在污染读数"）；
   ② 主动连续切换 GPADC 通道，看 THS 码是否跟随跳变（判断是否共用模拟前端/参考）；
3. **示波器量模拟参考网络**：VCC-ADC（W7）、VCM-ADC（Y9，外接电容脚）、VREFN-ADC（Y10，参考负）
   的纹波，空载 vs 满载对比 —— 预期能看到与码值跳变同步的扰动，这就能把"耦合路径"钉死；
4. **核对这三脚的去耦电容与地回流**（VCM-ADC 手册明确要求外接电容），以及模拟地与数字地的分割；
5. 若以上都排除，则回到结论：SoC 内部模拟前级在负载瞬态下自身不稳（需原厂确认，软件侧用去毛刺兜底）。

## 3. 根因分析

### 3.1 排除：真实过热 / 散热不足

* 正常态（两簇最高频）只有 47~52 ℃，启动峰值也只是 ~70 ℃，距离 110/130 ℃ 很远；
* 误触发时从 51.8 ℃ 到 >130 ℃ 仅 ≤0.14 s，需要 ≈480 ℃/s，与实测最快真实速率 7.5 ℃/s 相差约两个数量级；
* 每次误触发都是**所有 ths 通道同时**跳变（含平时恒为错值的 ddr 通道），真实热点不会让四个不同位置的传感器在同一毫秒内一起跳；
* 同期 PMU（AXP2202）温区只有 34~45 ℃，平缓变化。

### 3.2 排除：校准数据缺失

见 2.3：CALIB 寄存器均为非默认值，说明 SID 校准数据存在且已被驱动写入。

### 3.3 排除：芯片/板卡损坏、供电异常、看门狗

* 每次都能完整引导到 `/init`，CPU/DDR/eMMC/以太网/显示/音频/SSH 全部正常；
* 关机后重新上电即恢复，读数回到正常量级；
* 关机日志完整（thermal critical → hw_protection_shutdown → forced poweroff），不是无日志的掉电或复位。

### 3.4 结论：读数被扰动 + 驱动缺少去毛刺 → 误保护

```
负载/电源域动作（启动 8.6 s 的 mali/npu/camera 模块加载、8 核满载、电源域上电）
   └─ THS 原始码在毫秒级骤降：~2050 → 650~750
        └─ 驱动按官方公式换算 = 130~141 ℃（见附录 B：高温区间走 (2825-code)×0.065）
             └─ 内核 1 Hz 轮询"恰好"命中该毫秒窗口（因此约 3/7~1/2 概率才复现）
                  └─ critical(130 ℃) 触发 → hw_protection_shutdown → reboot: Power down
```

扰动表现出的规律（三条特征同时成立）：

1. **全通道同步**：cpul / cpub / gpu / npu / ddr 同时跳，PMU 温区不跳；
2. **毫秒级**：≤0.14 s 完成 +67 ℃ 的跳变，且同一秒内 sysfs 与直读寄存器互相矛盾；
3. **与负载/电源域动作绑定**：启动 8.6 s（GPU/NPU/摄像头电源域上电）与 8 核满载都能触发。

因此这更像 **THS 模拟前级/采样被电源或时钟扰动打歪**（芯片/板级的模拟鲁棒性问题，也可能与
`CLK_GPADC1_24M` 采样时钟或模拟参考在负载突变时的行为有关），而驱动**完全没有异常值剔除**，
把单次被扰动的样本当成真实温度直接上报，于是误触发了不可逆的保护关机。

### 4.3 判读规则

* **假读数（本次结论）**：某一通道或多通道原始码在毫秒级骤降（如 2050 → 700），而其它通道/PMU 温区不同步；
  或同一秒内 sysfs 与直读寄存器互相矛盾；
* **真实升温**：多通道同步、连续数秒缓慢下降（升温）、松开负载后回落，速率量级 ≤10 ℃/s。

## 5. 修复建议

### 5.1 首选：驱动侧去毛刺（本次问题的直接修复）

在公共入口 `sunxi_ths_get_temp()`（`bsp/drivers/thermal/sunxi_thermal.c`，第 223 行附近）加最小滤波，
对所有芯片/通道统一生效，不改芯片相关的 `get_temp` 实现：

```c
/* sunxi_thermal.h: struct tsensor 增加两个字段（无条件，不依赖 CONFIG_AW_THERMAL_CRITICAL_HANDLER） */
	int	deglitch_last;	/* 上次采信值(mC) */
	int	deglitch_cnt;	/* 连续突变计数 */
	int	deglitch_valid;

/* sunxi_thermal.c */
#define SUNXI_THS_DEGLITCH_JUMP_MC	30000	/* 单次突变阈值 30C */

static int sunxi_ths_get_temp(void *data, int *temp)
{
	struct tsensor *s = data;
	struct ths_device *tmdev = s->tmdev;
	int ret, t;

	ret = tmdev->chip->get_temp(s, &t);
	if (ret)
		return ret;			/* 保留原有 -EAGAIN 语义 */

	if (s->deglitch_valid) {
		int d = t - s->deglitch_last;
		if (d < 0)
			d = -d;
		if (d > SUNXI_THS_DEGLITCH_JUMP_MC) {
			/* 单次突变（毫秒级扰动）先不采信，要求连续 2 次一致才接受 */
			if (++s->deglitch_cnt < 2)
				t = s->deglitch_last;
		} else {
			s->deglitch_cnt = 0;
		}
	}
	s->deglitch_last = t;
	s->deglitch_valid = 1;
	*temp = t;
	return 0;
}
```

性质说明：

* 毫秒级扰动只影响 1 次采样，会被"沿用上次有效值"挡掉；内核轮询是 1 Hz，所以相当于要求异常必须持续 ≥2 s 才采信；
* 真实过温（持续升温）最多延迟 1 个轮询周期（1 s）就被接受，保护功能不受影响；
* 建议同时把 `sun55iw3_ths0_get_temp()`（DDR 通道）在异常时也走同一套逻辑，或该温区在 DTS 中移除。

> 交付方式建议：以 patch 形式放在 `模块/Linux/T527_thermal/`（本仓跟踪目录），再 `git apply` 到 SDK；
> 不直接改 SDK 源码树（按仓库约定 SDK 目录不入库）。**该补丁尚未实施，需确认后进行。**

### 5.2 不推荐：继续抬高 `critical`

扰动峰值达 136~141 ℃，把 `critical` 抬到 130 ℃ 已经无法规避；继续抬（150/200 ℃）等于取消保护，
遇到真实过温就没有兜底。**`OKT527-C-Common.dtsi` 末尾那段 130 ℃ 临时诊断代码应在修复后回退**
（板级默认 115 ℃，die 级基础值 110 ℃）。

### 5.3 需向飞凌/全志确认的问题

1. T527 的 THS 采样时钟（`CLK_GPADC1_24M`）/ 模拟参考，在 **GPU/NPU/摄像头电源域上电瞬间**或**满载电流突变**时
   是否会被扰动？是否有 errata 或官方驱动补丁？
2. 本板 ths0（DDR 温区）原始码恒在 2270~3155 乱跳（读数 -12~+44 ℃），校准寄存器 `0x0200A0A0=0x82B` 已写入，
   是否属于已知问题？
3. 是否有推荐的软件规避方式（Allwinner 其他平台是否已有"去毛刺/多次确认"的实现可参考）？

### 5.4 顺带处理项

* `ddr_thermal_zone` 读数不可用：在 DTS 移除该温区，或驱动侧屏蔽异常值，避免后续误导判断；
* GPADC CH3（板级温度传感器，位于 SoC/核心板附近）：单次读数噪声 ±150 mV（≈±17 ℃），8 次平均后仍有
  649~736 mV（≈15~24 ℃）的跨样本漂移，**当前不能作为绝对温度基准**，需按 `模块/OpenHarmony/opT527_gpadc.md`
  复核采样率/settling/通道配置后再用。

### A. 寄存器与换算（依据 `T527_User_Manual_V0.90.pdf` 2.16.6 节）

**ths1（CPU/GPU/NPU 传感器）** `0x02009400`，`#thermal-sensor-cells = <1>`：

| 偏移 | 名称 | 说明 |
|---|---|---|
| `0x00` | CTRL0 | T_ACQ / FS_DIV |
| `0x04` | ENABLE | 传感器使能位 |
| `0x08` | PC | TEMP_PERIOD |
| `0x20` | DATA_INTS | 数据有效状态（驱动要求 `sts & BIT(id)`） |
| `0x30` | MFC | 滤波器控制 |
| `0xA0`/`0xA4` | TEMP_CALIB | 校准 cdata（默认 0x800，非默认=已校准） |
| `0xC0 + 4*id` | TEMP_DATA | id0=cpub、id1=cpul、id2=gpu、id3=npu |

**ths0（DDR 传感器）** `0x0200A000`：数据寄存器 `0x0200A0C0`，校准 `0x0200A0A0`。

**换算公式**（`sun55iw3_calc_temp()`，单位均为 ℃）：

```
code >  1991 : T = (2736 - code) * 0.074    ← 覆盖 55 ℃ 以下（常温/低温）
code <= 1991 : T = (2825 - code) * 0.065    ← 覆盖 54 ℃ 以上（高温走这一支）
```

> ⚠️ 高温必须用第二支：**130 ℃ ↔ code ≈ 825**、110 ℃ ↔ 1133；正常态 code ≈ 2000~2050 ↔ 47~51 ℃。
> （早期文档里"130 ℃ ↔ 979"的说法有误，已在本文与 README 更正。）
